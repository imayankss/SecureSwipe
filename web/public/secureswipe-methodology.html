A fraud detector is easy to make look good. On the population evaluated here, 96.52% of transactions are legitimate — so a model that answers “legitimate” to every row scores 96.52% accuracy and catches nothing. SecureSwipe is built against exactly that trap.

It ranks suspicious transactions so a finite team of analysts spends the day on the ones most likely to be fraud. Against a sealed held-out population of 88,581 transactions it ranks at 6.0× the no-skill baseline, surfaces 80.18% of all fraud inside a 1,000-review daily budget, and returns probabilities calibrated to within 0.36 percentage points. The payment decision stays with the analyst: the system does not authorize, approve, capture, block, or decline.

Capacity is the second constraint, and it is the real product. A team works a fixed number of cases a day, and every point of recall above that line is bought with analyst hours. Section 4 puts that control in your hands; Section 5 prices it under assumptions you set.

Every number here is transcribed from committed aggregate evidence in docs/evidence/ and the exported dashboard data under web/data/. No row, score vector, or model binary appears on this page — and none is needed to check the arithmetic.

Reading the two lanes correctly

The metrics above come from the sealed offline evaluation. The local API and the /demo walkthrough run a separate reference bundle that demonstrates the serving mechanics — validation, thresholds, replay, audit — and does not inherit those metrics. Sections 1, 6 and 8 describe that reference path.

01 Architecture and decision path

Three lanes are kept apart by design: the offline science that produced the sealed result, the static pages that present it, and an optional local API that demonstrates the serving mechanics. Nothing crosses between them except sanitized aggregates.

  1. Accept only authorized or sanitized input. The static surfaces read committed aggregates; the optional demo sends one fixed synthetic fixture to an explicitly configured local API.
  2. Validate before scoring. Strict named schemas reject unknown, malformed, non-finite, or oversized input. Missing or invalid bundles fail closed.
  3. Score deterministically. A verified local bundle normalizes fields into its recorded order and executes the estimator. There is no LLM call on this path and it consumes zero tokens.
  4. Apply the recorded policy. Score meaning, calibration status, and the operating threshold come from bundle provenance — not from browser assumptions.
  5. Return a bounded outcome. A valid result is human_review or below_review_threshold; errors return no decision at all. Neither outcome is a payment action.
  6. Record and replay truthfully. When audit is configured a successful decision receives a chained receipt, and an identical request replays the original response without scoring or appending again.

02 Sealed evaluation protocol

A held-out number is only worth reading if nobody could have peeked. The corpus is split by time, not at random: roles are assigned chronologically, and every tunable choice — model family, variant, calibrator, capacity policy — is made inside a development boundary that never sees the final_test rows.

When that work finished, the pipeline, its 24-input schema, and the capacity policy were frozen and bound to a digest. Only then did a guarded runner score the held-out role once, seal the scores, and open the labels. The protocol then closed: no re-tuning, no second run, no quiet re-fit. It is a programmatic hold-out, enforced in code rather than by an external party.

03 Held-out performance

These are the numbers the sealed protocol produced, on a population where fraud is 3.4804% of traffic. Average precision reads against that base rate, not against 1.0: a signal-free ranker scores 0.034804 here, so 0.208660 is 6.0× the no-skill floor. ROC-AUC of 0.814975 confirms the same separation pairwise across all 88,581 rows, and an expected calibration error of 0.003556 means the reported probabilities hold to within 0.36 percentage points.

Ranking intervals are 95% bootstrap confidence intervals over 2,000 resamples at seed 42. Calibration intervals are analytic normal approximations at the same sample size, labelled in the final column and derived below the table.

Table 1 Sealed Lane A final metrics, with the interval method stated per row.

Analytic intervals use the Wald normal approximation at n = 88,581. For the Brier score and the calibration error, per-row variance is bounded conservatively at μ(1−μ) for a statistic on [0, 1], so those two intervals are upper bounds on the true width. The log-loss interval assumes a per-row dispersion of σ ≈ 3μ, typical of a calibrated model at this prevalence. All three are computed for this page; the frozen record stores those measures as point estimates.

Lane B is a different corpus, and is not a comparison

The repository also preserves an older record on a separate credit-card corpus — 284,807 rows at 0.1727% prevalence, average precision near 0.8288. That number is higher than everything in Table 1 and it means nothing here: different corpus, base rate, label definition, feature space, and a random rather than chronological split. It is kept for provenance, never as a comparison.

04 The review-capacity frontier

A score is half a decision. The other half is how many cases a team can review in a day — that budget, not the model, is what fixes the threshold. Take the top N ranked transactions per day and every increase in N buys recall with analyst hours.

What a false positive is here

A false positive is a legitimate transaction sent to human review. It is not an automatic decline, a blocked card, or a lost customer. Whether it becomes any of those depends on what the reviewing analyst does next, which is outside this system entirely.

05 The capacity–cost model

Section 4 produces a workload. Pricing it takes constants the evaluation cannot supply, so the model is stated as symbols first and the numbers are left to you.

For a review capacity B, SecureSwipe selects the top-B ranked transactions — the rule behind Figure 4 and Table 2:

QB  =  TopB{ si }

That selection fixes four counts — TPB, FPB, FNB, TNB — and with them the two operating curves already plotted in Figure 4:

Recall(B)  =  TPBTPB + FNB          AlertPrecision(B)  =  TPBTPB + FPB

Pricing the queue adds three assumed constants, none of them measured by the sealed evaluation: cr, the analyst-review cost per alert; cl, the additional legitimate-customer friction per false alert; and cm, the assumed cost of a missed labelled fraud. The illustrative total cost at capacity B is then:

C(B)  =  cr(TPB + FPB)  +  cl·FPB  +  cm·FNB

So cr, cl, and cm are inputs, not findings. The calculator asks for four rupee values rather than three — missed-fraud loss and chargeback handling are entered separately, then summed into cm. Replace the placeholders with your own and the chart recomputes C(B) at every frozen tier.

How to read C(B)

No displayed capacity is claimed to be optimal. C(B) is sensitivity arithmetic over published aggregate counts under constants you supply — not Razorpay economics, observed merchant cost, or ROI. The sensitivity is the finding; the rupee totals are yours.

06 Trust boundary

A boundary is worth more written down than promised. Every component is listed below with what it sees, what it cannot reach, and what it emits. None of them touches a PAN, a CVV, live Razorpay traffic, or a real customer, and none performs a payment action.

The feature names are not permission

Lane A's inputs are benchmark fields. They are not a licence to infer a person's identity or behaviour, and the anonymized V1–V28 PCA components must not be reverse-labelled with invented merchant, customer, or device semantics. They have no such meaning.

07 Evidence discipline

Evidence is sorted into six categories, and each one is bound to the claims it may support. Synthetic fixtures prove the plumbing works and nothing about fraud detection. A local bundle responding correctly proves the API behaves and inherits none of the sealed metrics. Exactly one category carries the headline numbers.

08 Replay and audit integrity

A system that scores the same transaction twice, or drops an audit event when the database blinks, is not auditable. The V2 path treats a request ID as a reservation: the reservation, the audit append, and the stored response commit together or not at all.

Four outcomes cover the whole design. A repeat of a completed request replays the original response and receipt without scoring again. A repeat with a different body under the same ID is a conflict, never a silent overwrite. A stale or failed reservation fails closed. Only a genuinely new request scores.

Tamper-evident, precisely

The chain makes modification detectable. It is not WORM storage, a compliance artefact, or a legal instrument, and local loopback behaviour is not a production SLO.

09 Reproduction

Raw datasets and trained fraud bundles are intentionally absent from the repository. Hash-locked Python closures and web/package-lock.json are the dependency sources of truth, so the environment below is pinned rather than resolved.

python3 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements/quality.lock
.venv/bin/python -m pip check

cd web && nvm use 22.13.1 && npm ci && cd ..

The gates that check every number quoted on this page:

.venv/bin/python -m ruff check api src scripts tests
.venv/bin/python -m mypy --ignore-missing-imports api src/artifacts src/inference
.venv/bin/python -m pytest
.venv/bin/python scripts/export_web_data.py --check
.venv/bin/python scripts/verify_historical_observation.py

cd web && npm test && npm run build && npm run test:e2e

The exporter checks aggregate evidence; it does not rerun the sealed evaluation, and nothing in this repository can. The historical verifier checks Lane B's lock and creates no new result. For a data-free repository check:

python3 -m scripts.run_project_audit --allow-missing-model --check
